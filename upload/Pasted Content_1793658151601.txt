3. Priority 0: Investigate existing runtime and audio integrity problems

This investigation is mandatory and must precede unrelated feature expansion.

The user has reported the following symptoms in the Round 21 PitchLab builds:

1. The three VST3 variants sound indistinguishable and appear to consume similar CPU resources.
2. Even with one voice, the output exhibits a Haas like stereo effect. A dual mono input develops a small relative channel offset.
3. The plugin has become internally unresponsive while the DAW survived. Audio output became completely silent even though the DAW meter showed maximum volume.
4. Small clicks and pops are audible in processed audio. These are especially noticeable with negative pitch shifts, where the sound becomes darker and the high frequency clicks become easier to hear.
5. The source audio is reported to be clean. The user does not attribute the issue to CPU overload or offline rendering.

Do not assume that all symptoms have a common cause.

4. Priority 1: Resolve the complete Minimum Pitch signal path

Round 21 identified the original UI Minimum Pitch control as C0 through B3, with a default of C2, approximately 65.406 Hz.

PitchLab currently has Config::f0_min, defaulting to 60 Hz, configurable between 20 and 200 Hz.

However, the downstream spacing logic retains an independent fixed 55 Hz gate. Lowering the detector minimum therefore does not prove that the complete pitch shifting engine supports the same frequency range.

Trace and document the complete signal path:

1. Minimum detector frequency.
2. Pitch tracker lag range.
3. Tracker confidence and rejection.
4. Period conversion.
5. Grain spacing.
6. Delay read position.
7. Voice pitch ratio.
8. Lower frequency safety constraints.
9. Buffer size and interpolation support.
10. Output frequency and latency behaviour.

Ensure each stage follows a coherent, explicitly documented minimum frequency policy.

Test these input frequency points:

32.703, 36.708, 41.203, 49.000, 55.000, 60.000, 65.406, 73.416, 82.407 and 110.000 Hz.

Test positive and negative intervals, including octave down and minus 24 semitones where mathematically and technically supported.

Separate the following capabilities in the API and documentation:

1. Frequency detectable by the tracker.
2. Frequency accepted as a valid pitch estimate.
3. Frequency safely supported by the delay and grain engine.
4. Frequency that can be shifted for a particular interval without violating buffer or spacing constraints.

Do not simply remove the 55 Hz spacing gate. First establish the real safety requirements and the valid range of every downstream stage.

Preserve 60 Hz as the default until the full low frequency path has been measured.

Update stale documentation, including the valid range comment in native/include/octavox/dsp.hpp.

5.2 Investigate CMNDF normalization start lag

The current implementation calculates CMNDF over a restricted lag range rather than necessarily accumulating the full difference function from lag 1.

The FullRate path begins normalization at its configured lower lag. The Decimated and Hybrid paths warm up from a limited number of lags below the configured minimum.

This may change the normalized values and the locations of threshold crossings. Its actual effect must be measured rather than assumed.

Implement an independent mathematical reference for comparison.

For identical input frames, record and compare:

1. Difference function values.
2. Cumulative normalization values.
3. CMNDF curves.
4. Candidate local minima.
5. Selected lag.
6. Interpolated lag.
7. Final frequency.
8. Confidence or voicing result.
9. Rejection reason.

Quantify the effect of the restricted normalization range across low notes, high notes, noisy frames and transient material.

Do not silently change the FullRate path simply to make the implementations appear more alike.

5.3 Threshold and interpolation comparison

The current PitchLab implementation uses a threshold of 0.20.

External reference implementations use different thresholds, including 0.10 and 0.40. These values are not directly comparable unless their normalization, search ranges and frame support are equivalent.

Run a controlled threshold sweep and measure octave errors, missed estimates, false voicing, jitter and latency.

Compare interpolation methods using the same candidate lag and difference function:

1. Parabolic interpolation of CMNDF.
2. Parabolic interpolation of the raw difference function.
3. FullRate current behaviour.
4. Decimated current behaviour.
5. Hybrid coarse and fine behaviour.

Determine which differences produce meaningful improvements and which are merely implementation differences.

Keep the default detector and interpolation unchanged until evidence supports a change.

5.4 Audit the hyuncat YIN reference

Reference:

https://github.com/hyuncat/YIN-algorithm

The repository contains an educational notebook using FFT autocorrelation.

The inspected implementation calculates a difference function using a constant full frame energy term and the autocorrelation. This is not generally equivalent to the conventional finite overlap difference function, which accounts for the two overlapping segments at each lag.

Independently verify the discrepancy using deterministic signals and direct numerical comparison.

The notebook also has the following limitations:

1. It is educational material rather than a validated real time production implementation.
2. The final best local estimate step appears to be missing.
3. Its synthetic generator accepts frequency and duration arguments but hardcodes 440 Hz and two seconds in the inspected code.
4. Repository metadata does not establish a reuse license.

Do not copy its implementation into PitchLab without a license review. It may be used as a mathematical reference after its limitations are documented.

5.5 Audit the ABSounds YIN reference

Reference:

https://github.com/ABSounds/YIN-Pitch

The inspected YIN_pitch.py implementation uses decimation, a difference function, CMNDF, threshold and local minimum selection, interpolation and frequency conversion.

The repository declares AGPL 3.0. Do not copy its source into a closed product without a separate license review.

The implementation has an important test target: its default frame size is 256 samples and its decimation factor is 8. At a 44.1 kHz input rate, the effective sample rate is approximately 5512.5 Hz. A 20 Hz signal has a period of approximately 276 decimated samples, which exceeds the nominal frame size.

Therefore the default configuration cannot robustly support 20 Hz and may produce invalid slice lengths or array dimension mismatches if lag and window constraints are not validated.

Verify this experimentally. Record the failure or invalid operating condition, and determine whether the implementation safely rejects unsupported configurations.

Also inspect its slice boundaries and CMNDF accumulation. Compare its conventions against the mathematical reference rather than assuming every discrepancy is a defect.

9.1 Randomize sign and modulation direction

Older R9 and R11 evidence indicates that an absolute value noise path produces a nonnegative modulation input. Round 21 contains language describing positive and negative rate modulation.

Resolve the contradiction explicitly.

Trace the random source, absolute value operation, scale conversion, polynomial mapping and final multiplier.

Distinguish:

1. Noise sign.
2. Modulation input range.
3. Rate multiplier range.
4. Cents deviation from baseline.
5. Polynomial approximation error.

The earlier derived relationship is:

page[10] = clamp(modamt / 2400, -1, 1)

The earlier rate path includes:

local_3f0[k] = 2^(cents / 1200) * 0.0625

and:

step = float32(P(f)) * slot_4128 * 64

with P(0) = 0.25.

Under the previously derived path, no modulation gives the intended base ratio after scaling. Recheck these relationships against the actual evidence and preserve any corrections.

R11’s corrected calculations indicated approximately 49.939 cents for F=1 and depth 50, and approximately 199.923 cents for depth 200. Earlier figures of 50.13 and 201.68 cents were calculation errors.

Verify these calculations independently and document the polynomial approximation error separately from the modulation direction.

Preserve the historical findings and add a correction record rather than silently overwriting them.
